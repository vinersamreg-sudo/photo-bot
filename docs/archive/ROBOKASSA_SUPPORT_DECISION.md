# Решение поддержки Robokassa по «Робочекам СМЗ»

Статус: историческое письменное подтверждение фискальной модели, полученное до
ребрендинга. Название Pixora ниже сохранено как часть исходного вопроса и ответа;
в активной интеграции та же модель использует наименование «Пакет доступа Ravuna».
Дата получения и фиксации ответа: 23.07.2026.  
Персональные данные сотрудника поддержки и служебные реквизиты обращения не сохраняются.

## Вопрос

Какие поля должен передавать самозанятый с активными «Робочеками СМЗ» при продаже цифрового продукта «Пакет доступа Pixora»: нужны ли `sno`, `payment_method`, `payment_object` и второй чек после использования пакета?

## Письменное решение поддержки

- В `Receipt` для самозанятого с активными «Робочеками СМЗ» можно не передавать `sno`, `payment_method` и `payment_object`: эти поля не несут смысловой нагрузки для формирования чека самозанятого.
- `Receipt` обязателен при инициализации платежа, участвует в контрольной сумме и передаётся URL-кодированным.
- Для GET-ссылки значение `Receipt` в самом запросе URL-кодируется дважды: один раз формируется представление для подписи, второй раз оно кодируется как значение query-параметра.
- Pixora продаёт одну цифровую услугу одной товарной позицией: «Пакет доступа Pixora», 49 ₽, две обработки фотографии и один оригинал без водяного знака.
- После подтверждённой оплаты формируется один чек. Использование обработок и права на оригинал является использованием уже оплаченного пакета и не создаёт новых чеков.
- Признаки аванса, предоплаты и полного расчёта в `Receipt` не передаются.

## Целевой Receipt

```json
{"items":[{"name":"Пакет доступа Pixora","quantity":1,"sum":49.00,"tax":"none"}]}
```

Инварианты:

- одна позиция;
- сумма хранится в backend как `4900` копеек и рендерится как `49.00`;
- сумма позиции равна `OutSum`;
- `Receipt` не бывает пустым;
- отсутствуют `sno`, `payment_method`, `payment_object`, `cost`;
- состав 2+1 описывается в `Description`, на сайте и в оферте, а не расширяется в `name`.

## Кодирование GET

1. Backend создаёт стабильный UTF-8 JSON без лишних пробелов.
2. JSON URL-кодируется один раз. Именно это значение входит в строку Password #1. Pixora передаёт дополнительные страницы возврата, поэтому фактическая строка:

   `MerchantLogin:OutSum:InvId:Receipt:SuccessUrl2:GET:FailUrl2:GET:Password1:Shp_order=...`

   Без URL2-модификаторов базовая форма была бы `MerchantLogin:OutSum:InvId:Receipt:Password1:Shp_order=...`. Модификаторы включаются только если соответствующие параметры реально передаются.
3. При сборке GET query это уже закодированное значение кодируется второй раз как значение параметра `Receipt`.
4. Первое декодирование query возвращает представление, участвовавшее в подписи; второе возвращает исходный JSON.

Подписывать одно представление и отправлять другое запрещено.

## ResultURL и одночековая модель

`Receipt` из браузера или callback не является источником истины для выдачи продукта. После валидного POST ResultURL backend проверяет SHA-256 Password #2, `OutSum=49.00`, `InvId`, локальный заказ, владельца и `Shp_order`. Одна SQLite-транзакция подтверждает платёж и идемпотентно начисляет +2 обработки и +1 право на оригинал. `OK<InvId>` возвращается только после commit.

SuccessURL и FailURL ничего не начисляют. Повтор ResultURL не создаёт второй пакет или второй чек продажи. Использование обработок, получение оригинала и повторная доставка оригинала не создают новые чеки. Локальная запись `receipt_type=refund` относится только к отдельному возвратному аудиту и не является вторым чеком продажи.

Не возвращаться к системе двух чеков без нового прямого письменного требования Robokassa или ФНС.
